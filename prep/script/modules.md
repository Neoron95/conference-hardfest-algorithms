# Выключаемые модули и пользовательская репетиция

Основной сценарий `full_script.md` имеет полный бюджет 32:55; выбранные короткие версии сокращают его до 31:55. Эти модули в его время не входят. В слоте 40 минут один модуль можно включить вместо сопоставимого объёма коротких версий, сохранив 8 минут на вопросы. Все три также пригодны для ответов после основной части.

Модули используют существующие backup-слайды и результаты. Переключение в backup и возврат к следующему основному слайду следует отрепетировать. Время ниже — расчёт, пользовательская репетиция ещё не проведена. Каждый модуль можно пропустить без разрыва истории.

## 1. `radixmin` — Почему можно убрать сравнения ключей

**Длительность:** 1:10. **Место:** после `flat`, перед `share-q`; либо ответ на «Почему не radix?».

**Вход.** «Перед следующей ставкой разберём кандидата, которого разрешило устройство нашего ключа».

**На экране.** Существующая схема radix: короткие шестнадцатеричные числа и проходы по полубайтам.

**Говорю.**
Поразрядная сортировка раскладывает элементы по одной части ключа. Здесь младший полубайт, затем старший. Важное условие: внутри группы сохраняется порядок предыдущего прохода. Уже разобранные младшие части остаются упорядочены, когда переходим к старшим.

В измеренной реализации шестидесятичетырёхбитный ключ обрабатывается восемью проходами по байтам. Вместо дерева сравнений получаем фиксированные проходы, счётчики и копирование. Цена — дополнительный буфер размером со вход.

Числовой ключ дал нам эту возможность. Но короткий массив, ограничение памяти или другой тип ключа могут изменить выбор. Одного названия radix тоже недостаточно.

**Выход.** «Вернёмся к дельте. Следующая ставка — как на знакомый выбор влияют повторы».

**Если пропускаю.** Переход `flat` → `share-q` из основного сценария самодостаточен.

**Под рукой.** На схеме учебные полубайты, в бенчмарке байты. «Без сравнений ключей» не означает отсутствие вычислений. Варианты radix для строк здесь не разбираются.

## 2. `learned-table` — Что показали контрольные опыты

**Длительность:** 1:15. **Место:** после `learned`, перед `qos`; либо ответ о повторяемости бенчмарка.

**Вход.** «Вот два отдельных опыта, которые помогают сузить объяснение».

**На экране.** Слева x86/Linux: один восстановленный вход 9,7; 64 одинаковые копии 9,6; 64 разных массива 46,9; разные входы через один буфер 8 КиБ — 46,8 нс/элемент. Справа отдельно: macOS/M2 — 6,8/14,4; качественный контроль M2/Linux VM — одинаковые копии тоже медленнее одного восстановленного массива.

**Говорю.**
Слева x86. Один восстановленный вход и одинаковые копии — около десяти наносекунд. Разные входы — около сорока семи.

Но могло ли дело быть в адресах? В четвёртой строке разные значения проходят через один буфер. Адреса одинаковые, результат всё равно дорогой. Повторяемость содержимого здесь влияет сильнее, чем смена буфера.

Справа другой процессор. Нативная macOS показывает знакомое удорожание на разных входах. Отдельный контроль в Linux-виртуалке: одинаковые копии тоже медленнее одного восстановленного массива. Причина для M2 остаётся гипотезой.

Эти опыты помогают разделить возможные объяснения. При этом мы сохраняем границу между окружениями и не склеиваем их в одно доказательство.

**Выход.** «Теперь входы фиксируем. Следующая переменная — режим исполнения самого потока».

**Если пропускаю.** Последний абзац `learned` уже переводит к `qos`.

**Под рукой.** Четыре x86-строки — данные текущей контрольной серии. Числа macOS — отдельное наблюдение; VM-контроль качественный. Не сравнивать абсолютные времена разных библиотек как чистый эффект ОС. Аппаратная причина для M2 не установлена этой таблицей.

## 3. `nb-lang` — Что скрывается за словом set

**Длительность:** 1:10. **Место:** после `platforms`, перед `review`; либо ответ о конкретном языке.

**Вход.** «Вот несколько разных способов хранить одно множество».

**На экране.** Существующая классификация контейнеров: узлы, открытая адресация, цепочки в массивах. Это устройство реализаций, не сравнительный бенчмарк языков.

**Говорю.**
У C++ unordered_set и Java HashSet есть отдельные узлы. В Java числовой ключ Long может добавить объект. Go с версии один двадцать четыре и Rust HashMap используют плоскую организацию.

У Swift и Python открытая адресация, но свои хешеры и представление значений. Число в Python обычно является объектом. В C# цепочки хранятся в массивах: слово «цепочка» ещё не означает отдельную аллокацию на ключ.

Это даёт кандидатов для проверки, а не готовые коэффициенты. Сначала узнаём устройство своего контейнера. Затем ставим вопрос к своим данным и среде. Название set — лишь начало разговора.

**Выход.** «Представьте тот же диф в вашем языке. Какой комментарий оставили бы коллеге?»

**Если пропускаю.** Переход `platforms` → `review` остаётся из основного сценария.

**Под рукой.** Конкретные типы, версии и оптимизации влияют на боксинг и аллокации. Не говорить «два объекта всегда». Swift/Python не считать узловыми таблицами. Здесь нет измеренных коэффициентов GC или иных хешеров.

## Репетиция с пользователем — ещё не проведена

Это описание следующей проверки готовой речи, не отчёт о выполненном прогоне.

1. **Первый полный прогон:** непрерывно пройти основной сценарий с реальными слайдами и кликером. Голосования играть с предусмотренными паузами; свободный ответ ограничить восемью секундами. Пятисекундную паузу `review` выдержать полностью.
2. Отметить время после `result` (4:55), `flat` (11:55), `inputorder` (16:55), `learned` (18:55), `flip` (26:55), `review` (31:55). Проверить, что финальная фраза звучит до 32-й минуты без ускорения технических объяснений.
3. Попросить слушателя объяснить три вещи: почему изменился лидер; что доказал опыт и где заканчивается вывод; какой комментарий он теперь оставит к исходному дифу. В ответе про опыт отдельно проверить различие между сменой лидера на 512K и разрывом ×3,3 на 1M. Если нужно повторно объяснять, уточнить переход и убрать соседнюю второстепенную реплику.
4. **Второй полный прогон:** ещё раз пройти все 28 основных слайдов, с исправленными переходами и выбранными короткими версиями. Проверить возврат задачи на `merge`, связку `qos` → `x33` → `core-model` → `cores`, переход `platforms` → `review`, спокойный финал. Записать фактические контрольные метки повторно.
5. После двух прогонов определить, нужен ли один дополнительный модуль и какой фрагмент он заменяет. Учитывать реакцию зала; расширение не компенсировать более быстрой речью.

**До прогона известно:** слова подсчитаны по тексту; порядок и число щелчков сверены с HTML. **До прогона неизвестно:** личный темп спикера, время реакции зала и фактический хронометраж. Критерий — ясная история и спокойный финал, а не достижение числа слов.
