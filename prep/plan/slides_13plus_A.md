Это переворот. Отмена — реальная статья расходов, но платит по ней сортировка, не хеш. Сортировка выигрывает не потому, что у неё всё гладко, а потому что хеш ждёт память дольше, чем она ждёт вахтёра.
И отсюда же — почему мой бенчмарк на одном входе врал: вахтёр выучил экзамен.

**Если отстаю.** Видео показать молча, сказать только: «девять промахов у сортировки, меньше одного у хеша — отмена платит сортировка; хеш проигрывает памятью».

**Футер.** «Xeon VM · симулятор ветвлений cachegrind (двухуровневый, не настоящий предсказатель): абсолютные числа завышены, порядок между алгоритмами устойчив · N = 2^20, U = N/2 · bench/deep/counters, bench/deep/branch».

**Под рукой.** Из 31 условного ветвления на элемент у сортировки промахиваются 9 (30 %); у хеша из 51 — 0,9; у flat из 12,5 — 1,5. Штраф на современных ядрах Intel 15–20 тактов [П]; 9 × 17 ≈ 150 тактов ≈ 50 нс при 2,8 ГГц — больше половины времени sort на x86; реальная доля меньше, потому что часть ошибок перекрывается, — оговорить «порядок величины». Подтверждение «от обратного» — следующий слайд. Миф «хеш постоянно сбрасывает конвейер» (встречается в чужих конспектах) — опровергнут этим числом.

**Производство.** Видео 10–12 с, две сцены (монетка / выученный ответ). Данные: `counters.csv`, колонки `Bc/el`, `Bcm/el`.

### 34. `sortfamily` — ОДНА НОТАЦИЯ — ТРИ СКОРОСТИ · 0:40 · новый

**Экран.** Доска: «Отмена». Три полосы У5, нс на элемент, 1M случайных, один харнесс: **std::sort 172** · **разбиение без ветвлений (pdqsort) 67** · **SIMD-сортировка AVX-512 6**. Подпись: «все три — O(n log n)». Мелко: «так уже сортируют JDK 23 и NumPy».

**Билды.** 1: std::sort. 2: pdqsort — ×2,6. 3: SIMD — ×29; штамп на доске закрыт.

**Говорю.**
Проверим вахтёра от обратного. [щелчок] Та же сортировка, но разбиение переписано так, чтобы сравнение не выбирало ветку: результат сравнения записывается как бит, элементы переставляются потом. В два и шесть десятых раза быстрее — ровно та часть, которую отнимал вахтёр.
[щелчок] Третий вариант сортирует векторными инструкциями, по восемь ключей за раз, без единого ветвления по данным: в двадцать девять раз быстрее стандартной. Все три — та же O(n log n). Один алгоритм на бумаге — три скорости на одном процессоре.
Хеш против сортировки — это не спор нотаций. Это спор реализаций за то, чего ждать: память или вахтёра.

**Если отстаю.** Одна фраза: «та же O(n log n): 172, 67, 6 — нотация одна, скорость разная».

**Футер.** «Xeon VM, libstdc++, N = 2^20 случайных uint64, один харнесс · std::sort / pdqsort_branchless / x86-simd-sort (AVX-512) · bench/deep/sort · libc++: 120 / 46 / 7».

**Под рукой.** В libc++ есть разбиение по битам из pdqsort, но в этой сборке std::sort для uint64 выигрыша не показал (120 против 120) — [уточнить причину по sort.md: инстанциация в .so / тип компаратора]. Поэтому со сцены «безветвенное разбиение — ×2,6» говорим про pdqsort, который мерили, а не про libc++. На iPhone std::sort берётся из системной dylib — алгоритм на телефоне определяет версия iOS. SIMD-вариант нужен AVX-512 или AVX2; на ARM у JDK — скалярный quicksort (beyond.md §2.3).

**Производство.** Три полосы У5 в бирюзовых оттенках. Данные: `bench/deep/sort/results/simdsort_avx512.csv` (`random,1048576`), `sortphase_gcc.csv`.

### 38. `boxes` — ТА ЖЕ ПРОГРАММА, ТРИ КЭША · 0:50 · новый

**Экран.** Доска: снова «Ожидание», подпись «на другом ядре». У6: три вложенные коробки в масштабе — **2 МиБ** (L2 Xeon), **4 МиБ** (L2 E-кластера), **16 МиБ** (L2 P-кластера); рядом таблица на 24 МиБ (миллион, половина уникальных) в том же масштабе — не входит ни в одну, таблица на 12 МиБ входит только в большую. Под коробками таблица «промахов последнего кэша на элемент, та же программа»:

| кэш | sort | узловая | плоская |
|---|---:|---:|---:|
| 16 МиБ | 0 | 0,9 | 0,4 |
| 4 МиБ | 0,2 | 2,5 | 1,3 |
| 2 МиБ | 0,7 | 3,6 | 2,0 |

**Билды.** 1: коробки и таблица на 12/24 МиБ. 2: строка 16 МиБ. 3: строки 4 и 2 МиБ — число 2,5 крупно.

**Говорю.**
Как проверить, что дело в коробке, если на телефоне нет счётчиков? Прогнать ту же программу через модель кэша разного размера. Это симулятор, не телефон, — но программа та же до инструкции.
[щелчок] Коробка шестнадцать, как у производительного кластера: сортировка не промахивается вовсе, узловая таблица — почти раз на элемент. На полумиллионе было четверть — вот та самая ступенька с восемнадцатого слайда, теперь посчитанная.
[щелчок] Коробка четыре, как у энергоэффективного кластера: у узловой таблицы два с половиной промаха на элемент, у сортировки — ноль целых две. В двенадцать раз. И каждый промах, вспомним, ждёт по одному.
Вот арифметика utility: та же программа, коробка вчетверо меньше, промахов у хеша втрое больше, у сортировки — почти столько же. Осталось убедиться, что телефон действительно сменил коробку.

**Если отстаю.** Только строка «4 МиБ: 2,5 против 0,2» и фраза «коробка меньше — хеш страдает первым».

**Футер.** «Симуляция cachegrind на Xeon VM, та же программа, размер последнего кэша 16 / 4 / 2 МиБ, N = 2^20, U = N/2 · не замер на A16: ёмкости 16 и 4 МиБ взяты с M2 Pro по sysctl, у A16 свои · bench/deep/counters».

**Под рукой.** Полный ряд по N при 16 МиБ [уточнить по counters.md §2]. Симулятор не знает префетчера и перекрытия — считает промахи, а не время; поэтому «втрое больше промахов» ≠ «втрое медленнее». Честный мост к ×5,8 на iPhone: промахи ×3 плюс меньше курьеров на E-ядре (гипотеза) плюс частота. Для A16 размеры L2 — из sysctl телефона (plan «что вписать»).

**Производство.** Схема У6: три рамки (масштаб 1 МиБ = 12 px), два прямоугольника таблицы, таблица чисел. Данные: `counters.csv`, колонка `DLmr/el` (+`DLmw/el`) при cache E/P/X.

### 43. `langs` — ТА ЖЕ СТРОЧКА В ВАШЕМ ЯЗЫКЕ · 1:00 · новый (модуль D)

**Экран.** Слева У1 лента: C++ `vector<uint64_t>` — числа в ячейках; ниже та же лента для Python `list[int]` — в ячейках не числа, а стрелки к разбросанным объектам по 36 байт; Java `ArrayList<Long>` — стрелки к объектам Long. Справа две полоски: Python, миллион случайных id: **`sorted` + unique 711** нс/эл · **`set` 142** — хеш быстрее в пять раз, наоборот к C++. Внизу короткая ставка: «вставить в отсортированный список 10 000 элементов: `std::list` — O(1) вставка, `vector` — сдвиг O(n). Кто быстрее?» → ответ **vector ×170**.

**Билды.** 1: ленты трёх языков. 2: полоски Python ×5. 3: ставка про список. 4: ответ ×170.

**Говорю.**
Та же строчка в вашем языке делает другую работу. [щелчок] В C++ вектор хранит числа. В Python список хранит указатели на объекты, в Java — ссылки на Long. Сортировка такого списка — это уже прыжки по указателям: тот же квест, что у узловой таблицы.
[щелчок] Проверил: в Python на миллионе случайных id `set` быстрее `sorted` в пять раз. Ровно наоборот, чем в C++, — потому что сортировка там стала узловой, а `set` в Python плоский.
[щелчок] И классическая ставка. Отсортированный список, десять тысяч элементов, вставляем новые по месту. Связный список — вставка за один шаг. Вектор — сдвиг хвоста. Кто быстрее? [пауза 3 с]
[щелчок] Вектор. В сто семьдесят раз. Сдвиг — это лента и курьеры, список — это коробки по одной. Страуструп показал это в 2012-м; с тех пор разрыв только вырос.
Язык не меняет физику — он меняет, где лежат байты.

**Если отстаю.** Убрать ставку про список, оставить Python ×5 и фразу «язык меняет, где лежат байты».

**Футер.** «Python 3.13, 1M случайных 64-битных int, медианы: bench/deep/langs/py · C++: std::list против vector с бинарным поиском, N = 10 000, вставки в позицию: bench/deep/langs/cpp · Java/Go/Rust — не измерено».

**Под рукой.** numpy sort + маска — 16 нс/эл: плоский массив возвращает сортировке победу. `np.unique` — 825 (сортировка объектов внутри? [уточнить]). Java `HashSet<Long>` — два объекта на ключ, ≈61–64 Б (beyond.md §2.1); Kotlin `distinct()` — `LinkedHashSet`, порядок первого появления. Go и Rust — плоские Swiss-таблицы, их sort безветвенный (pdqsort/ipnsort) — не мерил. Контроль механизма на C++: сортировка через указатели на разбросанные объекты 470–570 против 191 нс/эл по значениям (`cpp_ptrsort.csv`). Список: при 100 000 — 501 мкс против 4,8 мкс на вставку (×100).

**Производство.** Ленты У1 в три ряда (значения / указатели / ссылки); две полоски; карточка-ставка янтарём. Данные: `bench/deep/langs/results/py_dedup.csv`, `cpp_listvec.csv`.
