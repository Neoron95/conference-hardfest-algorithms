Почему хешу так дорого ждать, а сортировке — нет? Посмотрим, как каждый из них ходит по памяти. Возвращаемся к миллиону разных id, как в первом замере, и к Маку.
Слева сортировка: обычный массив, ключи лежат подряд по восемь байт. Следующий ключ всегда по соседству, и соседи приезжают из памяти вместе.
[щелчок] Справа unordered_set. Массив ячеек хранит не ключи, а адреса. Каждый ключ живёт в отдельном узле где-то в куче. Чтобы найти ключ: читаем ячейку, по адресу из неё идём в узел, из узла — к следующему.
[щелчок] Вот главное различие. У сортировки следующий адрес — это текущий плюс восемь байт. Процессор знает его заранее и может запросить данные наперёд. У хеша следующий адрес лежит внутри текущего узла. Пока узел не приехал из памяти, процессор просто не знает, куда идти дальше.
[щелчок] Это видно по выгрузке результата в массив. Это просто обход всех узлов — считанные команды на число. А занимает она четверть всего времени хеша: тринадцать с половиной наносекунд из пятидесяти пяти. Работы почти нет — одно ожидание. Сколько стоит одно такое ожидание — на следующем слайде.

Под рукой
• Устройство: и libstdc++, и libc++ держат все узлы в одном односвязном списке; ячейка хранит указатель на узел перед первым узлом своей корзины. Поиск — цепочка зависимых чтений: ячейка → узел → следующий узел. Узел: libc++ 24 Б (next + кешированный хеш + ключ), libstdc++ 16 Б; у malloc оба — 32 Б.
• Фазы unordered_set на M2 (bench/mac/results/m2/E11_phases.csv, N = U = 2^20, два повтора): вставки 30,3 нс (55 %), выгрузка 13,5 (24 %), деструктор 11,8 (21 %), всего 55,3. iPhone P — 31,9 / 13,7 / 11,5.
• Команд выгрузки на ARM отдельно не мерили; на x86 (callgrind) — 10 на число. Это цикл: прочитать ключ, записать, перейти по next.
• Промахи L1 на число (счётчики M2, U = N): sort 0,77 · uset 9,19 — в 12 раз больше; промахи TLB 0,01 против 3,6 (m2/counters_ui.csv). На CI (cachegrind, строка 64 Б): 1,46 против 5,56.
• Деструктор — тоже обход списка: free по каждому узлу.
• Xeon-вариант слайда — в колоде V10.
