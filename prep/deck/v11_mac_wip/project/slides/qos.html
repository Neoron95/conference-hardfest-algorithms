Помните письмо тестировщиков из начала? Мак — ничья, CI — хеш, айфон — сортировка больше чем вдвое. Вот разгадка. Код и входы прежние. Меняем одну строчку: говорим системе, что работа несрочная, как у нашей фоновой синхронизации. Бенчмарк выставляет QoS потоку через этот API. Мы сообщаем системе срочность, а планировщик выбирает исполнение. На Linux этого API нет.
[щелчок] Полмиллиона id, половина уникальных. M2 Pro при обоих режимах даёт близкие результаты. На iPhone при высоком QoS тоже близко.
[щелчок] А iPhone в utility: сортировка около сорока семи наносекунд, таблица около ста шести. Лидер поменялся, sort быстрее больше чем вдвое. Ровно те числа из письма. Я тестировал. Просто не там. [пауза 2 с]
Мы поменяли режим потока. Он повлиял на алгоритмы по-разному. [щелчок] И Мак так умеет: в самом низком режиме, background, система уводит работу на энергоэффективные ядра — и там сортировка тоже быстрее вдвое.
[щелчок] А на миллионе id тот же айфон в utility — в три и три десятых раза. Не тридцать три — запятая тут важна.

Источники и условия
Один и тот же код (dedup_bench, E2), Apple clang 21 + libc++, N = 2^19, U/N = 0,5, sort / unordered_set нс на элемент:
• M2 Pro (m2/E2.csv): userInitiated 20,9 / 22,0; utility — не мерили (на слайде «—»; замер m2c, run_utility.sh); background 94,5 / 212,2 (sort ×2,25; E-ядра ≈1 ГГц, шумно ±20 %).
• iPhone 14 Pro, A16, iOS 27 (приложение HashBench, iphone-20261012-1304/E2.csv): userInitiated 21,5 / 20,3; utility 46,6 / 105,8 (×2,27); background 156,0 / 216,9.
• 1M, iPhone utility — 47,9 / 159,4 (×3,3, строка «на миллионе»).
QoS ставится через pthread_set_qos_class_self_np; влияет на выбор ядра, не гарантирует его тип. На Linux этого API нет. Swift Task(priority:) не измерен.
Строка «на миллионе» — бывший слайд x33 (скрыт): iPhone utility, 1M, U = N/2: 47,9 / 159,4 = ×3,33; userInitiated 22,2 / 24,8; 4M utility ×6,6. Универсальное правило про utility не выводим.
