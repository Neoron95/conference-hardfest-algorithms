Везде половина id разных, как в нашей синхронизации. В клетке — кто быстрее и во сколько раз; сравниваем алгоритмы внутри машины, не машины между собой.

CI: хеш впереди до полумиллиона, сортировка — только на самом большом входе. Мак и айфон на производительном ядре: почти ничья, на больших входах — сортировка. Айфон в utility, на энергоэффективном ядре: сортировка уже с двухсот пятидесяти тысяч, на четырёх миллионах — в шесть с половиной раз.

Источники и условия
U = N/2, нс на элемент, порог «≈» — 5 %. Пересчитано из CSV 12.10:
• CI: bench/results/E2.csv (gcc 13 / libstdc++, медиана трёх сессий s1–s3): sort / uset / flat — 64K 73,7 / 44,8 / 23,8; 256K 79,4 / 61,8 / 31,3; 1M 87,1 / 85,5 / 35,1; 4M 98,1 / 134,4 / 47,0.
• Mac P: bench/mac/results/m2/E2.csv (ui): 64K 19,2 / 18,2 / 14,4; 256K 20,3 / 19,7 / 14,8; 1M 21,4 / 25,4 / 16,5; 4M 22,5 / 53,4 / 20,6. Хеш ×1,06 на 64K — на границе порога.
• iPhone P: iphone-20261012-1304/E2.csv (ui): 64K 19,8 / 18,5 / 14,4; 256K 21,0 / 19,8 / 15,0; 1M 22,2 / 24,8 / 17,3; 4M 23,4 / 57,1 / 23,5.
• iPhone E: тот же файл (utility, E-ядра 2 ГГц): 64K 41,4 / 39,9 / 28,5; 256K 45,2 / 70,9 / 48,3; 1M 47,9 / 159,4 / 71,4; 4M 51,3 / 336,1 / 95,5.
• Полные карты (1K–4M, U = N, N/2, N/10, плюс Mac E и iPhone 0,6 ГГц) — bench/mac/results/THREE_MACHINES.md §3–4. При 10 % разных хеш выигрывает почти везде; при 100 % сортировка обгоняет unordered_set везде, а flat быстрее сортировки на CI (×1,3–2,5) и на P-ядрах Apple до 256K (×1,1–1,2); на E-ядрах — сортировка.
• Hosted macOS-раннеры GitHub — VM с одним типом ядер: QoS там не уведёт поток на E-ядро.
• Mac utility (m2c/E2.csv): 512K sort ×1,3, 1M sort ×2,1 — полной строки нет.
• Та же таблица против flat_hash_set — следующий слайд flip-flat.
• Прежние версии — скрытые flip-v2 (две таблицы, со щелчками) и flip (три колонки, данные V9).
