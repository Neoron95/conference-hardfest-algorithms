Ответ — в том, как написана сортировка. Возьмём одну и ту же быструю сортировку в двух вариантах. Первый — как в учебнике: на каждом сравнении прыжок по ответу, и процессор его угадывает. Сорок восемь наносекунд на число, восемь ошибок.

[щелчок] Второй — без ветвлений: ответ записываем как ноль или единицу, а элементы переставляем потом. Угадывать нечего — ошибок меньше двух. Команд при этом почти вдвое больше, а быстрее в два с половиной раза. Разницу во времени делим на разницу в ошибках — около шестнадцати тактов на ошибку. Это и есть цена выброшенной работы.

[щелчок] Стандартная std::sort на Маке, в libc++ от Apple, устроена как второй вариант. На CI, в libstdc++, — как первый.

[щелчок] Поэтому на CI сортировка втрое медленнее, чем могла бы: девяносто две наносекунды вместо тридцати. Это ещё вернётся.

Если спросят «почему без ветвлений быстрее и зачем тогда ветвления»
• Коротко: ветвления выгодны, когда процессор угадывает. На случайных числах — монетка: лишние команды дешевле выброшенной работы. Для строк и сложных сравнений трюк не работает — поэтому он не везде по умолчанию.
• Расчёт: 8,35 × 16 ≈ 135 из 172 тактов выброшены. Без ветвлений 184 команды вместо 102, но 2,8 за такт вместо 0,6 → 66 тактов.
• История: быстрая сортировка — 1961, ошибка тогда стоила пару тактов. std::sort в libstdc++ — introsort из STL 90-х. Без ветвлений — BlockQuickSort (Edelkamp, Weiß, 2016), pdqsort (Peters); libc++ — с LLVM 16 (2023), libstdc++ — пока нет.
• Предсказуемые данные (почти отсортировано, много повторов): процессор угадывает, ветвления почти бесплатны, а безветвенный вариант всё равно платит командами. Не мерили — в замерах только случайные числа.
• Только простые типы: число сравнивается одной командой, сразу 0 или 1; строки и свой компаратор дорогие и сами с ветвлениями. Поэтому libc++ и pdqsort идут без ветвлений только для арифметических типов и std::less.

Под рукой
• Слева — pdqsort() с лямбда-компаратором (с std::less pdqsort сам выбирает безветвенный путь), справа — pdqsort_branchless: один и тот же код, разное разбиение. bench/mac/sortfam.cpp, M2 Pro P-ядро (m2/sortfam.csv): 48,17 / 18,74 нс на число; std::sort 18,94; radix LSD 6,40. ×2,6 на слайде = 48,17 / 18,74 = 2,57 (до branchless); до std::sort — 2,54.
• Счётчики (m2b/counters_ui.csv, только сортировка, 1M): с ветвлениями 171,9 такта / 102,2 команды / 8,35 ошибки (0,59 команды за такт); branchless 66,0 / 184,0 / 1,81 (2,79); std::sort 66,6 / 212,6 / 1,61 (3,19).
• 16 тактов: (171,9 − 66,0) / (8,35 − 1,81) = 16,2; по времени (48,17 − 18,74) нс / 6,54 ≈ 4,5 нс ≈ 16 тактов при 3,5 ГГц. Нетто: у branchless на 82 команды больше, поэтому настоящая цена ошибки не меньше 16.
• Как устроено «без ветвлений» (BlockQuickSort, pdqsort): блок из 64 элементов сравнивается с опорным, номера пишутся в буфер — offsets[n] = i; n += (a[i] < p); — потом пары переставляются циклом без условий по данным.
• std::sort на Маке: 18,9 нс, 1,6 ошибки — как branchless. Безветвенное разбиение — upstream LLVM libc++ (с LLVM 16, cpp.md §4); в upstream 18 было выключено ошибкой в type trait, не зависит от архитектуры (sort.md §1.1), в main исправлено. В сборке Apple работает — видно по счётчикам.
• CI сегодня (Xeon VM model 207, gcc 13 / libstdc++, xeon207/sortfam.csv): std::sort 92,4 ≈ pdqsort с ветвлениями 95,3; pdqsort_branchless 30,2 (×3,1); radix 26,5. Раньше на VM с AVX-512: std::sort 58, branchless 22, x86-simd-sort 6 (колода V10).
• iPhone P: 19,6 / 49,7 / 18,4; iPhone E 2 ГГц: 44,0 / 80,6 / 38,6 (iphone-20261012-1304/sortfam.csv).
• Radix на Маке — 6,4 нс, втрое быстрее std::sort (18,9 / 6,4); с unique — 7,5 против 19,3, ×2,6.
• Прошлая версия — скрытый sortfamily-v2.
