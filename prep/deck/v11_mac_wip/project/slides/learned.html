Здесь я сам наступил на грабли. Вход перед каждым вызовом восстанавливается, поэтому мы каждый раз сортируем исходные данные.
[щелчок] На M2 один и тот же вход даёт шесть целых восемь десятых наносекунды на элемент, шестьдесят четыре разных входа — четырнадцать целых четыре. На Xeon контраст сильнее: девять целых семь и сорок шесть целых девять. Для iPhone этой серии нет.
Маленький повторяемый экзамен процессору достаётся снова и снова. Но одной пары чисел для объяснения мало.
[щелчок] На Xeon шестьдесят четыре одинаковые копии по разным адресам остаются быстрыми. А шестьдесят четыре разных входа через один буфер в восемь кибибайт — медленными. Значит, важен рисунок входа, а не адреса.
Это поддерживает гипотезу предсказателя; аппаратных счётчиков в виртуалке нет, а на нативной macOS механизм пока не разделён. Пора допросить третьего подозреваемого.

Источники и условия
N = 1024, U = 512 (Xeon E5: один вход 9,7, 64 разных 46,9, 64 копии 9,6, 64 через один буфер 46,8). M2 native 6,8 / 14,4 — сохранённое наблюдение V9; контроль с копиями на M2 шёл в Linux VM и с нативным опытом не объединяется. Симулятор кэша на x86 исключает объяснение через кэш: промахов D1 и LL нет ни в одном варианте; предсказатель-симулятор вход не «выучивает» (4,96 = 4,96 = 5,00), потому что проще настоящего (counters.md §5 п. 3). Идея: Lemire, «Benchmarking is hard: processors learn to predict branches», 2019.
