Источники и условия
Один и тот же код (dedup_bench, E2), Apple clang 21 + libc++, N = 2^19, U = N/2, sort / unordered_set, нс на элемент. Режим ставится pthread_set_qos_class_self_np (строка кода со слайда убрана).
• M2 Pro: userInitiated 20,9 / 22,0 (m2/E2.csv); utility 22,5 / 28,5 — sort ×1,27 (m2c/E2.csv, отдельный прогон; контроля ui в той же сессии нет); background 94,5 / 212,2 (×2,25, E-ядра, шумно ±20 %).
• M2 utility, E1, 1M все разные: sort 20,6 / uset 126 / flat 25,5 / radix 9,2 (в ui 19,3 / 55,2 / 18,5 / 7,5).
• Почему на Маке слабее: sort в utility почти как в ui (+7 %) — работа, судя по всему, осталась на P-ядре (на E-ядре было бы ≈40–95). Хеш медленнее: +30 % на 512K, ×2,3 в E1. Лестница M2 в utility (m2c/probe_utility.csv, слайд cores-v3): P-ядро, 3,2 ГГц, но за 8 МБ чтения в разы дороже (12 МБ — 26,7 нс против 11,2 в ui; 24 МБ — 115 против 26). Чем сильнее алгоритм ждёт память, тем больше замедление: uset ×2,3 > flat ×1,4 > radix ×1,2 > sort ×1,07. На iPhone utility — E-ядро 2 ГГц (слайд cores-v3).
• iPhone 14 Pro, A16, iOS 27 (HashBench, iphone-20261012-1304/E2.csv): userInitiated 21,5 / 20,3; utility 46,6 / 105,8 (×2,27); background 156,0 / 216,9 (×1,4).
• Строка «на миллионе» (1M, U = N/2, utility): Мак 22,9 / 48,8 = ×2,1 (m2c/E2.csv), айфон 47,9 / 159,4 = ×3,3. В userInitiated на 1M: Мак 21,4 / 25,4 (×1,2), айфон 22,2 / 24,8 (×1,1). Айфон 4M utility ×6,6. Мем про запятую и x33 скрыты.
QoS влияет на выбор ядра, не гарантирует его тип. Swift Task(priority:) не измерен. Прежняя версия — скрытый qos (строка кода, строка CI, M2 background вместо utility).
