Подозреваемый номер два — ожидание. Как его проверить? Если бы всё время уходило на работу, цена одного числа почти не зависела бы от размера входа: вставка в таблицу одна и та же. А если процессор ждёт память, цена должна прыгнуть в тот момент, когда данные перестанут помещаться в кэш. Значит, меняем размер входа.
Прогон по размерам у нас есть на Маке — возвращаемся туда. И в этой серии половина id повторяется, как в нашей синхронизации. Поэтому числа здесь не такие, как в первом замере. По горизонтали — сколько чисел, по вертикали — наносекунды на число.
[щелчок] Сортировка растёт плавно: чем больше чисел, тем больше сравнений на каждое — это и есть log n.
[щелчок] Хеш на крошечных размерах дороже — там заметна постоянная плата за вызовы аллокатора. Дальше линии сходятся, и на полумиллионе хеш даже чуть быстрее. А потом — излом: на миллионе дороже на треть, на четырёх миллионах — в два с половиной раза. Вставка та же самая. Добавилось ожидание. [пауза 2 с]
[щелчок] Где излом? Кэш второго уровня у M2 Pro — шестнадцать мегабайт. На полумиллионе таблица занимает двенадцать — влезает. На миллионе — двадцать четыре — уже нет.
[щелчок] Проверим на симуляторе, где кэш задан ровно шестнадцать мегабайт. Промахов мимо него на одно число: две десятых на полумиллионе, почти один на миллионе, почти два на двух миллионах. У сортировки — ноль. Второй подозреваемый на месте. Осталось понять, почему хешу так дорого ждать, а сортировке — нет.

Под рукой
• Время: prep/research/apple.md, исходная curve V9, M2 Pro / macOS / libc++ / userInitiated, U = N/2. Значения с графика: 512K — sort 19,6 / uset 18,7; 1M — 20,1 / 26,3 (×1,3); 2M — 20,9 / 40,1; 4M — 21,5 / 55,7 (×2,6). Это не та ×2,6, что в первом замере (там все id разные, 1M).
• Размер: узел 24 Б → 32 Б у аллокатора, ячеек N по 8 Б: 32·U + 8·N = 12 МиБ на 512K, 24 МиБ на 1M (+ вход 4 / 8 МиБ). apple.md, строка про cachecost (исправлено: у аллокаторов Apple нет заголовка, квант 16 Б).
• Промахи: cachegrind на Xeon, модель последнего кэша 16 МиБ (как L2 P-кластера M2), gcc/libstdc++, U = N/2: uset 0,19 / 0,23 / 0,94 / 1,91 на 256K / 512K / 1M / 2M; sort 0,00 (counters.md §2). Это симуляция, не счётчики M2: без префетча и без SLC Apple.
• «Работа не зависит от N» — инструкции по N не мерили; при reserve вставка не меняется, у сортировки растёт log N.
• Малые N: на 16 элементах sort ≈3 нс, uset ≈13 нс — постоянные расходы вызовов new/delete и хеширования; к 1K линии сходятся.
• Почему серия U = N/2, а не «все разные»: в материалах (apple.md, исходная curve V9) прогон M2 по размерам опубликован для неё; для U = N в колоде используется точка 1M.
