Почему хешу так дорого ждать, а сортировке — нет? Посмотрим, как каждый из них ходит по памяти. Возвращаемся на Xeon и к миллиону разных id, как в первом замере.
Слева сортировка: обычный массив, ключи лежат подряд по восемь байт. Следующий ключ всегда по соседству, и соседи приезжают из памяти вместе.
[щелчок] Справа unordered_set. Массив ячеек хранит не ключи, а адреса. Каждый ключ живёт в отдельном узле где-то в куче. Чтобы найти ключ: читаем ячейку, по адресу из неё идём в узел, из узла — к следующему.
[щелчок] Вот главное различие. У сортировки следующий адрес — это текущий плюс восемь байт. Процессор знает его заранее и может запросить данные наперёд. У хеша следующий адрес лежит внутри текущего узла. Пока узел не приехал из памяти, процессор просто не знает, куда идти дальше.
[щелчок] Это видно по выгрузке результата в массив. Это просто обход всех узлов — десять команд на число. А занимает она четверть всего времени хеша. Работы почти нет — одно ожидание. Сколько стоит одно такое ожидание — на следующем слайде.

Под рукой
• Устройство: и libstdc++, и libc++ держат все узлы в одном односвязном списке; ячейка хранит указатель на узел перед первым узлом своей корзины. Поиск — цепочка зависимых чтений: ячейка → узел → следующий узел. Узел: libstdc++ 16 Б (next + ключ), libc++ 24 Б (+ кешированный хеш); у malloc оба — 32 Б.
• Фазы unordered_set (counters.md §3, Xeon, gcc/libstdc++, N = U = 2^20): вставки 319 команд и 43 % времени, выгрузка 10 команд и 25 %, деструктор 130 команд и 28 %. Выгрузка — 1,64 промаха мимо последнего кэша на число.
• Промахов L1 на число (cachegrind, строка 64 Б, U = N): sort 1,46 · uset 5,56 — в 3,8 раза больше. При U = N/2: 1,57 · 3,94.
• Деструктор — тоже обход списка: free по каждому узлу.
