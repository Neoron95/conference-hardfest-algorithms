Backup · без шагов. Вопросы: «Почему не отсортировать только дельту и слить?» (qa X1), «set_union не убирает дубли дельты» (C5), «std::flat_set — это flat_hash_set?» (C10).
Ответ: Для нашей задачи это правильный ответ, он же на слайде merge. Сортируем дельту, схлопываем в ней повторы и сливаем с отсортированными локальными id через set_union или inplace_merge + unique. Без unique по дельте set_union оставит её дубли: из второго диапазона он берёт max(n − m, 0) копий — на 1,06 млн осталось 32 966 дублей. На x86 это в 3,5–6,6 раза быстрее sort + unique и в 4–6 раз быстрее flat_hash_set. libc++ в sort + unique быстрее libstdc++ (31 против 42): вход уже на 94% отсортирован. iPhone: Серия на телефоне не снималась; не домерил — «на телефоне ещё не мерил, цифры появятся в репозитории», не «будет так же».
std::flat_set — не хеш-таблица, а отсортированный вектор; его insert(range) в libc++ — ровно этот рецепт: отсортировать хвост, inplace_merge, unique.
INSERT OR IGNORE в SQLite (X10) — B-дерево и журнал, ожидаю медленнее, не мерил. Битовая карта для плотных rowid (X5): 1M id — 125 КБ, не мерил.
Мостик: лучший алгоритм использует то, что о данных уже известно, — здесь «SQLite уже отсортировала».

Условия и источники (были в подвале слайда): L — 2^20 локальных id (отсортированы, уникальны) + дельта D — 2^16, половина — повторы · x86-повтор на отдельной VM (Xeon 2,1 ГГц; GCC 13, Clang 18), медиана сессий · так вставляет диапазон std::flat_set в libc++
С экрана убрано: Исходный заголовок: «Сортируем только дельту и сливаем: на x86 в 3,5–6,6 раза быстрее sort + unique». Код: std::sort(D.begin(), D.end()); D.erase(std::unique(D.begin(), D.end()), D.end()); — без этого шага set_union оставит дубли дельты; std::set_union(L.begin(), L.end(), D.begin(), D.end(), std::back_inserter(out)). radix + unique: 41,4 / 39,8 нс/эл, быстрее sort + unique в 1,0 / 0,8 раза. sort(Δ) + unique(Δ) + inplace_merge + unique: 6,7 / 8,6 нс/эл, быстрее в 6,3 / 3,6 раза.
