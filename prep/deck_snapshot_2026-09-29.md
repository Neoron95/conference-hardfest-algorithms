На бумаге второй способ делает в двадцать раз меньше шагов. Я тоже сначала выбрал бы хеш-таблицу и закрыл тикет. Давайте проверим интуицию — вашу и мою.

// контракт: вход можно портить, выход — уникальные в том же векторе, порядок любой

Один и тот же набор проверок для всех: крайние случаи (пусто, один элемент, все равны, 0 и UINT64_MAX), разные N, доли уникальных и порядки, все контракты. Быстрое, но неправильное решение в турнире не участвует.
[SPEAKER NOTES]
6:30–7:15. Правила, иначе любое сравнение можно оспорить. Вход — вектор id, его можно портить. Выход — уникальные значения в том же векторе, порядок любой. Один набор проверок для всех реализаций: пустой массив, один элемент, все одинаковые, ноль, максимальное число, разные размеры и порядки. Верхняя оценка роста работы: N log N растёт чуть быстрее линии, N² — за край задолго до конца. Между O(N) и O(N log N) на миллионе — множитель около 20.
Время ≈ N × шагов × цена шага
Big-O знает только средний множитель. Цена шага — от 1 до 100 нс, два порядка; log₂(10⁶) — множитель 20. Память может перевесить логарифм в пять раз.
[SPEAKER NOTES]
7:15–8:15. Big-O отвечает на один вопрос: как растёт число шагов, когда растёт вход. Вдвое больше данных — примерно вдвое больше работы для линейной модели, чуть больше для N log N. Это по-настоящему полезно: Big-O спасает от катастрофы, когда данных станет в тысячу раз больше. Но время — это N, умноженное на число шагов, умноженное на цену шага. Big-O знает только средний множитель. Цена шага — от одной наносекунды за сложение в регистре до ста за поход в оперативную память: два порядка. А логарифм миллиона — двадцать. То есть память может перевесить логарифм в пять раз. Весь доклад — про этот последний множитель. → Переход: «Значит, надо посмотреть, из каких шагов состоит каждый соперник. Начнём с сортировки».

Упрощённая схема исследованных узловых реализаций (libstdc++, libc++) · учебный hash и 8 ячеек · стандарт требует, чтобы ссылки на элементы переживали rehash · libc++: число ячеек не степень двойки → номер ячейки через целочисленное деление, на ARM оно не бесплатно · max_load_factor 1.0
[SPEAKER NOTES]
9:00–10:15. Хеш-функция превращает ключ в номер ячейки — как библиотечный каталог превращает название в номер шкафа. Ключ 42, посчитали хеш, взяли остаток от деления на число ячеек — вот шкаф; на слайде учебный пример с восемью. Две детали для телефона: в libc++ число ячеек — не степень двойки, поэтому «остаток» — настоящее целочисленное деление на каждую вставку, а на ARM оно не бесплатно; и коэффициент заполнения по умолчанию 1.0 — reserve(N) выделяет N ячеек, без reserve таблица растёт удвоением и перевешивает все узлы. Два разных ключа в одном шкафу — коллизия; узловая реализация решает её цепочкой: в шкафу записка, где лежит первая книга, а в книге — где следующая. Цепочки в среднем короткие, отсюда «O(1)». Про хеш-функцию: для целых чисел std::hash — тождество, для моих случайных id это идеально; с реальными id проверьте гистограмму цепочек. Самое важное для нас: каждый узел — отдельный кусок памяти, отдельный вызов new. Стандарт требует, чтобы ссылки на элементы переживали рост таблицы, и узлы — привычный способ это выполнить. 15:15–16:00. Ещё один участник, про которого часто забывают: поразрядная сортировка, radix sort. Она вообще не сравнивает числа — а значит, на неё не действует нижняя граница N log N для сортировок сравнением. Ключ — восемь байт. Берём младший байт, раскладываем числа по 256 корзинам, как письма по ячейкам на почте. Потом следующий байт, и так восемь раз.
